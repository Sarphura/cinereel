# ADR-0005：使用命名空间标识扩展 DriveContentType

- 状态：已接受
- 日期：2026-08-20

## 背景

Drive 必须具有内容类型，扫描 Module 根据内容类型选择电影、剧集、音乐或通用文件的扫描机制。Cinereel 未来还需要允许官方或第三方扩展提供新的内容类型和扫描 Implementation。

如果使用 C# `enum` 表达内容类型，每增加一个扩展都必须修改并重新发布核心程序集。如果把 C# 类名直接持久化，代码重构会破坏已有 Drive。如果由每个实例安装时生成标识，同一个扩展在不同 Cinereel 实例上又无法获得一致身份。

因此需要一种稳定、可读、可跨实例交换，并且不依赖具体 Implementation 的开放类型标识。

## 决策

- Drive 持久化一个必填 `DriveContentTypeId`，不持久化展示名称、图标或 Scanner 的 C# 类型。
- `DriveContentTypeId` 使用稳定的命名空间字符串，官方与第三方扩展通过各自命名空间避免冲突。
- Cinereel 内置标识为 `cinereel.movie`、`cinereel.series`、`cinereel.music` 与 `cinereel.generic`。
- 持久化格式把 `DriveContentTypeId` 视为可扩展标识，不使用封闭的 C# `enum` 固化长期可选值。
- 当前版本只支持四个内置标识，不实现官方或第三方扩展的发现、安装、注册或动态加载。
- 当前扫描 Implementation 只需解析内置类型，不为尚不存在的第三方提供方预建插件 Seam。
- 扫描调用方不在 Controller、任务调度器或 Drive Module 中维护按类型分支；具体扫描 Module 的 Interface 在实现扫描能力时确定。
- Hyper Client 的 `metadata`、`blob` 等存储类型只属于 Hyper Client Adapter，不映射为 DriveContentTypeId。
- HTTP Interface 交换稳定的 DriveContentTypeId；当前 CreateDrive 只接受四个内置标识。
- 持有 DriveOwnership 可以修改 DriveContentTypeId，Subscription 不能修改该值。
- DriveContentTypeId 真正变更时，类型更新、旧类型 Scanner 产生的派生结果失效，以及完整重扫任务的可靠受理必须保持一致。
- 类型变更的 HTTP Adapter 在可靠受理完整重扫后返回 `202 Accepted`，不等待扫描完成；调用方通过独立扫描状态观察最终结果。
- 重复设置当前 DriveContentTypeId 是幂等操作，不使扫描结果失效，也不重复触发重扫。
- 完整重扫最终失败时保留新的 DriveContentTypeId，不恢复旧类型或旧派生结果。
- 失败的扫描状态保存安全的错误摘要并允许显式重试；技术异常与原始错误只进入日志。
- 扫描失败不会自动改用 `cinereel.generic`。
- 同一 Drive 同时最多存在一个未完成的 DriveScan。
- 当前 DriveScan 尚未进入成功或失败终态时，修改 DriveContentTypeId 返回 `409 Conflict`，不排队新的类型变更。

未来启用扩展时，必须另行决定命名空间所有权、扩展发现与加载、发布者信任、代码隔离，以及 Drive 引用的类型当前不可用时的行为。Drive 根目录中的内容当前一律视为数据，不作为可自动安装或执行的扩展代码。

## 备选方案

### 使用封闭的 C# enum

此方案类型安全，序列化和 OpenAPI 生成也很直接，适合永远只有固定内置值的模型。

但第三方无法在不修改核心程序集的情况下添加值，所有扫描调用方也容易形成中央 `switch`，因此不采用。

### 安装时分配 Guid

此方案可以在单个实例内保证唯一，也不需要协调字符串命名空间。

但同一扩展在不同实例上会获得不同标识。Drive 内容或描述在实例之间交换后，接收方无法仅凭 Guid 找到对应扩展，还需要额外的映射协议，因此不采用。

### 持久化 C# 类型名

此方案可以通过反射直接定位 Scanner，注册代码较少。

但类名、命名空间和程序集名称都是 Implementation 细节；重命名或拆分程序集会破坏历史数据，也会把领域模型与插件加载技术绑定，因此不采用。

### 使用无命名空间的短字符串

此方案保留可读性，内置 `movie`、`series` 等值也与现有 Web 契约兼容。

但不同官方或第三方扩展可能注册相同名称，系统无法稳定判断标识归属，长期只能依赖安装顺序解决冲突，因此不采用。

### DriveContentTypeId 创建后不可修改

此方案不需要处理扫描结果失效和完整重扫，Drive 的类型始终稳定。

但用户选错类型或内容用途变化时只能重新创建 Drive 并迁移文件，操作成本过高，因此不采用。

### 只允许空且未发布的 Drive 修改类型

此方案可以避免已有扫描结果和外部内容受到类型变化影响。

但修改资格同时依赖文件数量与 Publication 状态，用户难以预测；内容已经存在时恰恰更可能需要纠正类型，因此不采用。

### 同步等待完整重扫

此方案只有在新类型扫描成功后才返回，调用方不会观察到类型已更新但扫描尚未完成的阶段。

但大型 Drive 的扫描时间不可控，HTTP 请求会长时间阻塞；连接中断也无法可靠表达扫描是否仍在继续，因此不采用。

### 只更新类型并要求手动扫描

此方案不需要可靠任务受理，类型更新可以直接返回成功。

但用户容易在更新后忘记扫描，系统会长期缺少与当前类型匹配的派生结果，因此不采用。

### 重扫失败时回滚旧类型

此方案可以在新扫描失败后恢复到变更前的类型和派生结果。

但扫描期间文件内容可能已经变化，旧结果不再可靠；自动回滚也会违背用户明确选择的新类型，因此不采用。

### 重扫失败时改用 cinereel.generic

此方案可以尝试生成通用文件结果，让 Drive 不至于完全没有派生数据。

但系统会静默改变用户选择并掩盖实际扫描故障，后续行为也与用户期望的类型不符，因此不采用。

### 最新类型变更优先

此方案允许用户随时纠正类型；新的 DriveScan 取代旧任务，只有匹配当前操作与类型版本的结果才能提交。

但 Implementation 必须取消或忽略旧任务及其迟到结果，引入额外的操作身份、版本仲裁与资源浪费；当前不需要这种并发能力，因此不采用。

### 顺序执行所有类型变更

此方案不会拒绝用户操作，也不需要取消已经开始的扫描。

但中间类型的扫描结果会在下一次变更时立即失效，队列可能消耗大量时间和存储却不产生可用结果，因此不采用。

## 后果

正面影响：

- 持久化格式不会用核心枚举封死未来官方或第三方扩展。
- 持久化数据不依赖 Scanner 的类名和程序集结构，可以承受 Implementation 重构。
- 类型标识可跨 Cinereel 实例和 Hyperdrive 内容交换。
- 当前实现范围不包含插件系统，可以先围绕四个内置类型完成 Drive Module。
- 类型选择错误可以原地修正，不需要重新创建 Drive。
- 类型更新不会被完整扫描时长阻塞，调用方可以观察独立扫描状态。
- 扫描失败不会暗中改变 DriveContentTypeId，用户可以修复问题后重试。
- 扫描期间拒绝再次改型，避免迟到结果和类型版本仲裁。

代价与约束：

- 编译器无法把长期类型集合表示为封闭枚举；当前入口仍需校验只接受四个内置标识。
- 持久化层需要把 DriveContentTypeId 作为受约束字符串保存，而不是数据库枚举。
- OpenAPI 与 Web 前端不能生成封闭枚举，必须把类型标识当作字符串并动态读取可用类型。
- 真正启用扩展前还需要新的安全与兼容性决策，当前 ADR 只保留稳定标识方向。
- 类型变更要求扫描 Module 支持可靠地废弃旧派生结果、受理完整重扫并公开扫描状态。
- 持久化设计必须保证类型更新与重扫任务受理不会出现一边提交、另一边永久丢失。
- 扫描失败期间派生结果保持不可用，读取 Interface 必须如实表达该状态。
- 长时间扫描会暂时阻止再次修改 DriveContentTypeId，HTTP Interface 必须明确返回冲突原因。
- 类型重命名会影响持久化身份；发布者必须把已发布的 ID 视为长期兼容契约。
